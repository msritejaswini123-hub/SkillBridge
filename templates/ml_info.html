How matching works

The whole scoring pipeline, in the open. No black boxes.

1. The rule-based engine (this is what your score is)

Every student-internship pair is scored on five factors. Each factor produces a 0–100% sub-score and a sentence explaining itself. The weighted sum is the match percentage you see.

FactorWeightHow it is measured
Skill match {{ (weights.skills * 100)|int }}% (matched required + ½ × matched preferred) ÷ (all required + ½ × all preferred)
Qualification {{ (weights.qualification * 100)|int }}% Degree is 65% of this factor, branch 35%. "Any Degree" scores full marks. B.Tech and B.E are treated as equivalents.
Location {{ (weights.location * 100)|int }}% Exact city or a Remote role = 100%. A nearby city in the same cluster = 85%. A different city = 25%.
Stipend {{ (weights.stipend * 100)|int }}% Meets or beats your minimum = 100%. Below it, the score is the ratio (offering Rs 8,000 against a Rs 10,000 minimum = 80%).
Experience & projects {{ (weights.experience * 100)|int }}% 40% prior experience (6 months = full marks), 60% whether your projects mention the skills or domain the role asks for.
Worked example. A B.Tech CSE student in Hyderabad expecting Rs 10,000–20,000, with Python, SQL and HTML, looking at a Python Developer Intern role in Hyderabad paying Rs 15,000 that requires Python, SQL and Flask:
skills 2 of 3 = 66.7% → 33.3 pts · qualification 100% → 20 pts · location 100% → 15 pts · stipend 100% → 10 pts · experience 0% → 0 pts. Total 78%, with Flask listed as the missing skill. Add Flask and a relevant project and the same role scores in the mid-90s.

Target: {{ info.target }} — the probability a recruiter shortlists this pairing. Why bother? The rule engine is a straight weighted sum, so it cannot express "below a 30% skill match nothing else rescues you" or "a great skill match in an unreachable city is still a no". The squared and interaction features let the regression capture both, which is why it re-orders borderline matches usefully.

How it is combined: ranking key = 70% rule score + 30% ML probability. The displayed percentage stays 100% rule-based, so the breakdown table always adds up.

3. Resume parsing

pypdf extracts the text of every page. That text is matched against a dictionary of canonical skills with their spelling variants, using word-boundary regexes that respect + and # — so C does not match inside "CSE", but C++ matches itself. Short names like ML and Go must appear capitalised, so the English word "go" is never read as the Go language.

This is a dictionary lookup, not ML — which means it is predictable, debuggable, and the student can always see and correct exactly what was extracted before anything is saved.
